## 二、P0 级问题（必须修复，共 9 项）

> 标注「已复现」的条目均经实际执行验证（项目 venv / node），非推测。主审另抽查 6 条，代码证据全部属实。

### A-1 HTML BOM 生成存在存储型 XSS（已复现）
`src/html_bom/generator.py:72` + `src/html_bom/templates/ibom.html:171`、`templates/verification_map.html:263-264`
`json.dumps(components, ensure_ascii=False)` 不转义 `<` 和 `/`，模板侧 `{{ components_json | safe }}` 又关闭了 Jinja2 自动转义。BOM 的 value/型号/描述来自用户 CSV、LCEDA 插件、LCSC API，均未净化。实测 BOM 值填 `</script><script>alert(1)</script>` 原样穿透。`main.py:255` 生成后自动 `webbrowser.open()`，恶意 BOM 导入即触发。verification_map 的 `overlay_json` 还含 LLM 生成文本，面更大。
**修法**: 模板改用 `{{ components | tojson }}`（Jinja2 内置，转义 `<>&'`），删除手工 dumps + `| safe`。

### A-2 前端 markdown 渲染 XSS 可被实体编码绕过（已复现）
`web/js/chat.js:285-299`
中和正则只匹配字面 `javascript:`/`data:`。用仓库自带 marked.min.js 实测：`[a](javascript&colon;alert(1))`、`&#58;` 变体原样产出 `<a href="javascript&colon;...">`，浏览器解码后可执行。攻击面：AI 输出可被导入的 BOM/知识库内容经提示注入污染；Eel 页面暴露的 `eel.*` Python 面等于交出本机操作权。
**修法**: 引入 DOMPurify（vendor 进 `web/vendor/`，与 echarts 同策略），或改写 marked `renderer.link` 用协议白名单（http/https/mailto）；实体变体补进 `test_web_render_safety.py`。

### A-3 多智能体审查：LLM findings 去重键全部塌缩为 ":"，关键问题只剩 1 条（已复现）
`src/agent/review_agents.py:520-522`（根因 469-479）
LLM 路径构造 `AgentFinding` 时 `rule_name`/`location` 均为默认空串，`key = f"{f.rule_name}:{f.location}"` 全部等于 `":"` → `_synthesize_critical` 把不同问题当重复丢弃。实测 2 critical + 1 major 输入，critical_issues 只剩 1。
**修法**: LLM findings 去重键改用 `title`（或 title+detail 哈希）。

### A-4 多智能体审查：LLM 失败被吞，五个 Agent 齐报"未发现问题，设计质量良好"（已复现）
`src/agent/review_agents.py:481-484`
`_llm_deep_analyze` 把所有异常（断网/JSON 解析失败/限流）内部吃掉返回 `[]`，短路了 `_process_agent_llm`（320-327 行）设计好的规则回退。实测：LLM 抛 ConnectionError + 1 条 ERROR 级违规 → 报告"设计质量良好"。对审查工具是方向性错误结论。
**修法**: `_llm_deep_analyze` 失败时 raise，让上层 except 走规则回退；`[]` 只保留"确无违规"语义。

### A-5 「清除本地数据」功能双向损坏
`main.py:434-443`（REST 版 `src/api/endpoints.py:527-538` 同病）
`SETTINGS_DIR == app_home()`，与 sessions.db、logs/ 同目录，且 `_store`/`_controller` 单例不重置：开发模式删库后旧单例重建空库 → `no such table: workspaces`；打包模式日志句柄被 FileHandler 持有 → Windows 下 rmtree 必抛 PermissionError，功能永远失败。附带：内存中 LLM API Key 不清除，用户以为"已全清"。
**修法**: rmtree 前 `logging.shutdown()`；删除后置空 `_store`/`_controller` 并清 `config.llm`。

### A-6 标准版 .json/.epro 解析器完全不换单位，10mil 坐标被当 mm
`src/pcb/parser.py:137-167`（`_parse_track`）、`204-209`（`_parse_via`）、`323-349`（`.epro`）
EasyEDA 标准版 JSON 坐标/线宽单位是 10mil（1 单位 = 0.254mm），字段直接命名为 `width_mm` 落库。后果：10 单位（实际 2.54mm）被当 10mm → 线宽/载流检查永不触发，全部间距类规则失真。`.epro2` 路径有 `MIL_TO_MM` 处理，这两个遗留路径静默错标尺度。
**修法**: 按格式做单位归一（×0.254mm）或收窄 `SUPPORTED_PCB_FORMATS` 并打 `unit=unverified` 警告；补"宽 10 → 2.54mm"回归测试。

### A-7 BOM 导入：数量列一个坏单元格毁掉整份文件（已复现）
`src/bom/parser.py:136`
裸 `int()`，单元格为 `"ABC"`/`"2 (盘)"`/`"1,000"` 时整个导入 ValueError 崩溃，用户只看到裸异常。
**修法**: `_safe_int()` 降级为默认值 + warning 记录行号。

### A-8 BOM 导入：含空格/# 的英文表头被 itertuples 静默丢弃（已复现）
`src/bom/parser.py:116,124-133` + 别名表 `43-52`
pandas itertuples 把非法标识符列名重命名为 `_0/_1/...`，`getattr(row, "Part Number", "")` 全部返回空串——而别名表明确声称支持 "Part Number"、"LCSC Part #"。JLC/LCSC 英文导出的 BOM 静默解析出空字段，后续合并/健康检查全在错误数据上运行且无任何报错。现有测试只用中文表头，测不出来。
**修法**: 改 `df.to_dict("records")` 按字典取值；补英文表头回归测试。

### A-9 ML 数据泄漏：模板展开后才切分，验证集 81% 与训练集逐字重复（实测）
`src/ml/generate_nlu_data.py:459-476`（同型 `generate_component_data.py:457-470`）
先随机填充展开模板、后随机切分，同文本可同时落进 train/val。实测现有产物：`nlu_train_train.json` 790 条仅 365 个唯一文本；NLU 验证集 150 条中 122 条（81%）与训练集逐字相同（元件集 26%）。val_acc/ECE 基本在测记忆而非泛化。
**修法**: 切分改为模板级 + 切分前按 text 去重；BERT 管线沿用同一数据文件，修后需同步重训。

## 五、测试覆盖评估

**1289 个测试质量整体偏高**：`test_acute_angle.py`、`test_agent_loop.py`、`test_boot.py`、`test_web_render_safety.py` 是行为级测试范本（覆盖乱序线段/并发租借/状态机全路径/真实 vendored marked 执行）；历史 bug 普遍有"修复-测试-注释"闭环。

**系统性缺口**（9 个 P0 全部处于盲区，P1 大部分也是）:
1. review_agents 的 LLM 路径（`review_with_llm`/`_llm_deep_analyze`/`_synthesize_critical`）零覆盖 → A-3/A-4 存活。

4. 训练/切分脚本零测试 → A-9 漏网。
5. 负样本缺失：TMP36 不应匹配 Buck、`15V` 不应命中 `5V`、>10mm 体跨格对应报间距。
6. 建议增加：对每个 function definition 做 `_dispatch_operation(name, schema 合成参数)` 冒烟（可抓 A 组 P1-5 类 TypeError）。

## 七、验收结论

**结论：有条件通过 —— 基础质量高，但 9 个 P0 修复前不应发布对外版本。**

- 测试全绿、无密钥泄漏、SQL/绑定/遍历等基础卫生全部达标，架构与并发治理高于同类项目平均水准。
- 但 P0 集中在三类："**给出虚假安全结论**"（审查去重丢失、LLM 失败装作没发现问题、串扰假检查、DRC 单位失真）、"**安全执行面**"（两处已复现 XSS、CORS null + 破坏性端点）、"**数据正确性**"（BOM 解析静默丢列、ML 验证集泄漏 81%）——对一款设计审查工具，第一类是最不可接受的。
- 建议修复顺序：A-3/A-4（审查可信度）→ A-6/A-7/A-8（数据正确性）→ A-1/A-2（安全）→ A-5/A-9 → P1 按模块批量处理。每项修复配一条钉死该缺陷的回归测试（本报告第五节列了对应测试缺口）。
